    easymeasure.backend.resources¶

    Resource management: low-level ports (COM / GPIB / USB / Ethernet / simulated).

    Responsibilities¶

    • Each physical port is represented by exactly one Resource object, so two instruments can never open the same port independently and fight over it.
    • By default a resource is exclusive: a second instrument asking for it gets a ResourceBusyError.
    • Shared ports (a GPIB bus behind a Prologix adapter, an RS-485 chain, a multi-channel controller ...) can be requested with shared=True. Access is then arbitrated: every I/O sequence must run inside with resource.transaction(owner): which grants a fair, FIFO, re-entrant lock. When ownership switches from one instrument to another an optional selector callback of the new owner is run (e.g. send ++addr 12).
    • Resources can be invalidated (e.g. after a hung call). The next transaction transparently reopens the port; stale handles held by abandoned threads are closed and ignored.

    Address formats¶

    ================================= =========================================== COM3 / ASRL3::INSTR serial port (pyserial, or pyvisa for ASRL) /dev/ttyUSB0 serial port (pyserial) GPIB0::12::INSTR pyvisa USB0::0x1234::...::INSTR pyvisa TCPIP0::1.2.3.4::inst0::INSTR pyvisa TCP::192.168.1.5::5025 raw TCP socket (built-in, no pyvisa needed) SIM::<name> simulated byte port (see drivers/simbus.py) DAQ::<device> NI-DAQmx device (DAQ::Dev1); no byte port, but one owner, so two drivers cannot share a DAQ card NONE or empty instrument without a port (DLL/software) ================================= ===========================================

    Each address belongs to one interface (interface_of): gpib, usb, tcpip (VISA LAN), tcp (raw socket), serial, daq, sim, none or other (any other VISA type). Drivers list the interfaces they accept (Instrument.INTERFACES); ResourceManager.discover finds the ports of this computer by interface, optionally with their *IDN?.

    FairLock ¶

    FairLock()

    Re-entrant, FIFO-within-priority lock with timeout.

    Plain threading.RLock is not fair: a fast loop (e.g. the monitor) can starve a sweep. Here waiters are served in arrival order, except that waiters with a better priority (the measurement thread) go first, so monitoring and GUI traffic never slow a running sweep down.
